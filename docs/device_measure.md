# 현장 기기 동작 조건 측정 (WBS 7.3)

현장 기기 기준 환경(`docs/device_spec.md`: CPU 4코어, 메모리 8GB, 스왑 없음, GPU 없음)에서 파이프라인이
메모리 안에 들고 시간 목표(탐지 → 설명 10초)를 지키는지 잰다.

담당: 박서연 / 상태: 노트북 4코어에서 VLM(llama-server)까지 넣어 실측 완료 (11/19)

## 방법

`tools/measure_device.py`. 파이프라인(`src/pipeline/run.py`)을 기준 코어 수에 묶어 끝까지 돌린다.

- 코어: 리눅스는 `taskset` 으로 묶고 OMP/MKL 스레드 수도 맞춘다. 윈도우는 psutil `cpu_affinity`
- GPU: `CUDA_VISIBLE_DEVICES` 를 비운다
- 메모리: 상한을 걸지 않고 0.1초마다 프로세스(자식 포함) RSS 를 재서 최대값을 기준과 견준다.
  같은 기기의 `llama-server` 프로세스도 찾아 함께 잰다
- 부품별 메모리: 탐지 모델, 지리 자료, 지형 격자를 하나씩 올리며 늘어난 양을 잰다
- 단계별 시간: 끝난 뒤 `alerts.jsonl`, `detections/`, `debug.jsonl` 에서 모은다(중앙값, 90%, 최대)

```bash
# llama-server 를 같은 기기에서 4스레드로 먼저 띄운다 (VLM 까지 잴 때)
llama-server -m Qwen2.5-VL-3B-Instruct-Q4_K_M.gguf --mmproj mmproj-Qwen2.5-VL-3B-Instruct-f16.gguf -t 4 --port 8099

python tools/measure_device.py --cores 4 --mem-gb 8 --report results/device_measure.md -- \
    --weights best.pt --frames sim/frames_scenario --geo-dir data/geo_jagok \
    --sim-terrain sim/terrain_jagok3d.json --vlm gguf --out results/device_run
```

WSL 에서 기기 전체를 기준에 맞추려면 `%UserProfile%\.wslconfig` 에 아래를 넣고 `wsl --shutdown` 뒤 다시 켠다.

```
[wsl2]
memory=8GB
processors=4
swap=0
```

### 파이프라인의 VLM 을 현장 구성으로 (`--vlm gguf`)

현장 기기의 VLM 은 llama.cpp(GGUF Q4_K_M)다(`docs/vlm_speed.md`). 파이프라인의 `qwen` 모드는 transformers +
bitsandbytes 라 CPU 에서 1장 180초가 걸려 현장 구성을 잴 수 없었다. 그래서 `--vlm gguf --vlm-url` 을 넣었다.

- 설명: 탐지 조각(긴 변 360)과 같은 질문, 스키마를 llama-server 의 `json_schema` 로 강제한다
  (`tools/measure_inputs_cpu.py` 의 요청과 같다)
- 검증기: 같은 448px 조각과 질문으로, 첫 토큰의 `top_logprobs` 에서 "예"/"아(니오)" 확률을 읽는다
- 이 환경에서는 모델을 받을 수 없어(외부 다운로드 막힘) 응답 형식만 흉내 낸 가짜 서버로 연결만 확인했다.
  실제 모델로는 시연 PC 에서 확인한다

## 측정 환경 (11/19)

| 항목 | 값 |
|---|---|
| 기기 | 박서연 노트북, Intel Core Ultra 7 255U, WSL2 (Linux 6.18) |
| 코어 / 메모리 / 스왑 | 4 / 7.8GB / 없음 (기준: 4코어, 8GB, 스왑 없음) |
| GPU | 쓰지 않음 (`CUDA_VISIBLE_DEVICES` 비움) |
| VLM | llama.cpp `llama-server` (소스 빌드), Qwen2.5-VL-3B-Instruct Q4_K_M + mmproj f16, `-t 4 -c 8192 -np 1` |
| 입력 | 자곡동 신고 시나리오 38장(`sim/frames_scenario`), `--sim-terrain`, 장 사이 대기 없음 |

파이프라인과 llama-server 가 **같은 4코어를 나눠 쓴다**(현장 기기 그대로).

## 결과 2: 처리 시간

| 단계 (중앙값) | VLM 없음 | VLM 포함, 고치기 전 | **VLM 포함, 고친 뒤** |
|---|---|---|---|
| 탐지 (장마다) | 170ms | 645ms (최대 2.5초) | **753ms** (90% 2.5초, 최대 3.1초) |
| 지리 조회 | 19ms | 46ms | 60ms |
| **탐지 → 알람** | 192ms | 612ms (최대 1.0초) | **1.3초** (최대 2.7초) |
| 검증기 1번 (448px 조각) | | 12.2초 | **11.1초** |
| VLM 설명 1번 (360px 조각) | | 10.5초 | **10.2초** |
| **알람 → 설명** (마지막 갱신 기준) | 101ms | 78.6초 | **26.0초** |
| 38장 전체 | 9.4초 | 112.6초 | 71.0초 |

- **알람은 VLM 이 돌아도 1~3초 안에 나간다.** 탐지가 VLM 과 같은 4코어를 나눠 써 170ms → 0.6~0.8초(가끔 3초)로 느려진다.
  그래도 장 간격(드론 시뮬레이터 2~5초)보다 짧다
- **VLM 설명 1번이 10.2~10.5초로 10초 목표를 조금 넘는다.** `docs/inputs_cpu.md` 의 9.3초(윈도우, 다른 노트북)와 비슷하다
- **검증기(11.1~12.2초)가 설명보다 비싸다.** 11/19 에 448px 이라 13초쯤으로 셈한 것이 맞았다
- 같은 사진을 llama-server 를 끄지 않고 다시 넣으면 이미지 캐시 때문에 설명 3.7초, 검증 0.14초처럼 거짓으로 빨라진다
  (한 번 겪음, `docs/vlm_speed.md` 와 같은 현상). 잴 때마다 llama-server 를 새로 띄운다

### 고친 것: 갱신마다 쌓이던 검증

처음 잰 알람 → 설명 78.6초는 설명이 느려서가 아니었다. 알람이 6번 갱신될 때마다 새 탐지를 검증기에 넣었고,
검증기는 줄 선 순서대로 12초씩 6번(약 72초)을 돌았다. 설명은 같은 llama-server 를 쓰므로 검증이 끝날 때까지
기다린 뒤에야 마지막 위치의 설명(10.5초)을 만들었다. 줄 서 있던 검증 대부분은 그 사이 또 갱신되어 결과를 버리는 일이었다.

`run.py` `check_update` 가 검증기를 부르기 **전에** 그 탐지가 아직 최신인지 본다(전에는 부른 뒤에 봤다).
고친 뒤 검증 6번 중 4번을 건너뛰었고(요약 "또 갱신되어 검증 생략 4"), **알람 → 설명이 78.6초 → 26.0초**가 됐다.
남은 26초는 하던 검증 + 마지막 검증(약 11초씩)을 기다린 뒤 설명(10초)을 만든 시간이다.

### 검증기 값이 기준 근처에서 흔들린다

고친 뒤 첫 측정(이미지 캐시가 남아 시간은 버림)에서 마지막 갱신 탐지의 P(연기)가 0.67 로 나와 기준 0.7 에 못 미쳐
위험도가 "확인 필요"로 바뀌었다. 다시 잰 측정에서는 통과했다. 같은 연기의 조각마다 0.7 근처를 오가므로,
갱신 때마다 다시 검증하면 위험도 표시가 바뀔 수 있다 (4.7 담당과 상의).

## 판단

| 조건 | 결과 | 기준 |
|---|---|---|
| 메모리 | 5.61GB | 8GB 안 (통과) |
| 탐지 → 알람 | 1.3초 (최대 2.7초) | 즉시 (통과, 장 간격보다 짧다) |
| 탐지 → 설명 (알람이 6번 갱신된 시나리오) | 26.6초 | 10초 (못 지킴) |
| 설명 1번 | 10.2초 | 10초 (조금 넘음) |

CPU 4코어에서 설명 10초를 지키려면 검증기가 설명 앞을 막지 않아야 한다. 고를 수 있는 것 (4.7 담당과 상의)

1. 검증 조각 448 → 224px (이미지 토큰 약 256 → 64, 검증 약 3초 추정). 헛탐지 거르기가 그대로인지 같이 재야 한다
2. 첫 알람만 검증하고 갱신된 탐지는 검증하지 않는다 (같은 사건이므로)
3. 설명을 먼저, 검증을 나중에 (알람은 이미 나가 있으므로 위험도 "확인 필요" 표시가 늦어진다)

> **11/28 (7.4, `docs/latency.md`)**: 실제 속도(1.5초에 한 장)로 재 보니 갱신 때문에 설명이 버려지는 문제가 더 컸다
> (첫 설명 83.7초). 같은 사건의 VLM 관찰을 다시 쓰게 고쳐 첫 설명 23.7초, 갱신된 판은 알람과 함께 설명이 붙는다.
> 위 1~3 은 첫 설명(검증 11초 + 설명 10초)을 더 줄이는 데 여전히 쓸 수 있다.
