# 큰 모델(7B)과 견준 속도와 정확도 (WBS 7.5)

요청서의 "무거운 모델 대비 경량 모델의 속도/성능 비교"에 답하려고, 지금 쓰는 3B 와 같은
계열의 7B 를 같은 사진과 같은 질문으로 돌려 봤다. 3B 가 못하던 일이 모델이 작아서인지도
함께 봤다.

담당: 이예진 / 상태: 측정 완료(11/17, 속도와 메모리는 11/18 에 스레드 4개로 다시 잼). 3B 를 그대로 쓴다

## 조건

| | 3B | 7B |
|---|---|---|
| 모델 | Qwen2.5-VL-3B-Instruct | Qwen2.5-VL-7B-Instruct |
| 파일 | Q4_K_M 1.93GB + mmproj f16 1.34GB | Q4_K_M 4.68GB + mmproj f16 1.35GB |
| 받은 곳 | `ggml-org/Qwen2.5-VL-3B-Instruct-GGUF` | `ggml-org/Qwen2.5-VL-7B-Instruct-GGUF` |

- 7B 는 4bit 로 줄여도 개발 노트북 GPU(4GB)에 올라가지 않는다(`docs/vlm_candidates.md`).
  그래서 두 모델 모두 CPU 실행 방식(llama.cpp `llama-server`, GGUF Q4_K_M)으로 돌렸다.
  3B 도 같은 방식으로 다시 돌려 나란히 놓았다
- 개발 노트북(Core Ultra 7 155H, 메모리 32GB), 전원 연결. 메모리 상한은 걸지 않았다
- 정확도는 100장 전체를 스레드 8개로 돌렸다. 시간과 메모리는 스레드 4개로 따로 쟀다
  (탐지 조각 12개, 사진 5장, 다른 실험 없이, 서버를 새로 띄운 직후)
- 평가셋 확정본 100장(연기 70, 굴뚝연기 15, 구름 15). 사진은 노트북 밖으로 내보내지 않았다

```
llama-server -m <모델>.gguf --mmproj <mmproj>.gguf -t 8 -tb 8 -c 8192 -np 1 --port 8099
python tools/vlm_gguf_compare.py verify --dets runs/verify_real/verify_real.jsonl \
    --images data/eval_100/images/eval --out results/model_size_verify_3b.jsonl
python tools/vlm_gguf_compare.py observe --facts results/eval_facts.jsonl \
    --images data/eval_100/images/eval --out results/model_size_observe_3b.jsonl
python tools/vlm_gguf_compare.py report --verify results/model_size_verify_3b.jsonl \
    --observe results/model_size_observe_3b.jsonl
```

서버의 모델만 바꿔 같은 명령을 `_7b` 로 한 번 더 돌린다.

### 잰 일 두 가지

| 일 | 입력 | 질문 | 읽는 값 |
|---|---|---|---|
| 후보 검증기 | 탐지 조각 448px (탐지 177개: 연기 131, 헛탐지 46) | 이 사진에 연기가 있는가 | 첫 토큰의 P(예)/(P(예)+P(아니오)) |
| 사진 전체 관찰 | 사진 전체, 긴 변 1024 (100장) | 연기 유무, 연기색, 불꽃을 JSON 으로 | 답한 값 |

검증기의 탐지 박스와 정답은 `tools/vlm_verify_real.py` 가 남긴 것을 그대로 읽었다. 자르는 법은
`src/pipeline/vlm_client.py` 와 같다. 사진 전체 관찰은 `tools/measure_short.py` 의 질문과 스키마다.

## 결과

| 항목 | 3B | 7B |
|---|---|---|
| 검증기 AUC | 0.917 | **0.939** |
| 검증기, 연기 탐지 남김 (문턱 0.7) | **130/131** | 124/131 |
| 검증기, 헛탐지 거름 (문턱 0.7) | 38/46 | **41/46** |
| 　연기 사진 속 다른 곳 | 36/40 | 39/40 |
| 　굴뚝연기 | 2/6 | 2/6 |
| 검증기 때문에 새로 놓친 연기 사진 | 0장 | 3장 |
| 검증기, 연기 탐지의 95% 를 남기는 문턱에서 헛탐지 거름 | 41/46 (문턱 0.83) | 41/46 (문턱 0.63) |
| 사진 전체, 연기 사진을 연기라고 함 | 48/70 | **53/70** |
| 사진 전체, 연기 아닌 사진을 아니라고 함 | 17/30 | 18/30 |
| 연기색 맞춤 (연기 사진 70장) | 21/70 | 26/70 |
| 답한 연기색 | 검은색 48, 없음 22 | 검은색 53, 없음 17 |
| 검증기 1회, 스레드 4개 (입력 295토큰) | 11.9초 (11.4 ~ 12.4) | 19.0초 (17.0 ~ 19.6) |
| 사진 전체 1장, 스레드 4개 (입력 861토큰) | 41.2초 (41.0 ~ 41.9) | 60.3초 (57.7 ~ 66.4) |
| 메모리, 모델을 올린 직후 | 4.6GB | 8.7GB |
| 메모리, 최대 (검증 12회와 사진 5장 뒤) | 5.4GB | 9.7GB |

### 정확도: 7B 가 조금 낫지만 못하던 일은 그대로 못한다

- **연기색은 7B 도 검은색 아니면 없음으로만 답한다.** 흰색이나 회색은 두 모델 모두 한 번도
  없다. 맞춘 수가 21 → 26 으로 는 것은 연기라고 답한 사진이 5장 늘어 흑색 라벨 사진을 더
  맞춘 것이다. 색을 가리게 된 것이 아니다
- **굴뚝연기는 7B 도 못 거른다.** 2/6 으로 같다
- **사진 전체에서 연기를 보는 것은 5장 는다**(48 → 53). 3B 만 맞힌 사진은 없고 7B 만 맞힌
  사진이 5장이다. 그래도 70장 중 17장을 놓친다. 탐지 모델은 같은 70장에서 64장을 잡는다
- **검증기는 순서를 조금 더 잘 매긴다**(AUC 0.917 → 0.939). 문턱 0.7 에서는 헛탐지를 3개
  더 거르고 연기 탐지를 6개 더 놓친다. 문턱을 모델마다 맞추면(연기 탐지의 95% 를 남김) 둘 다
  헛탐지 41/46 으로 같다
- 3B 가 못하던 것은 모델이 작아서가 아니었다. 답이 한쪽으로 쏠리는 것과 굴뚝연기를 못
  가르는 것은 크기를 2.3배로 키워도 남는다

### 속도와 메모리: 1.5배 느리고 메모리를 세 배쯤 쓴다

- 스레드 4개에서 검증기 1회 11.9초 → 19.0초(1.6배), 사진 전체 1장 41.2초 → 60.3초(1.5배)
- 메모리는 올린 직후 4.6GB → 8.7GB, 최대 5.4GB → 9.7GB 다. 7B 는 올리기만 해도 8GB 를 넘어
  대표 기기로 잡은 소형 기기(메모리 8GB)에 올라가지 않는다. 개발 노트북 GPU(4GB)에도
  올라가지 않는다
- 스레드 8개로 100장을 돌릴 때는 검증기 7.9초와 11.9초, 사진 전체 26.7초와 43.2초였다.
  비율은 같다(1.5~1.6배)
- 100장을 다 돌린 뒤 7B 서버의 최대 메모리는 16.3GB 였다. 요청 277번을 이어서 처리하는
  동안 늘어난 것이다. 3B 는 같은 조건에서 재지 않아 견줄 수 없고, 왜 느는지도 확인하지 않았다
- 그래서 3B 를 그대로 쓴다. 7B 로 바꾸면 풀리는 문제가 없고, 현장 기기에 올릴 수 없다

## 함께 알게 된 것: CPU 실행 방식에서의 검증기

검증기를 CPU 실행 방식으로 돌린 것은 이번이 처음이다(지금까지는 GPU, bitsandbytes 4bit).

- **AUC 는 같다.** CPU 방식 0.917, GPU 방식 0.916 이다. 탐지마다의 차이는 중앙값 0.011 이다
- **문턱 0.7 은 조금 낮다.** 177개 중 6개가 0.7 을 사이에 두고 판정이 갈려, 헛탐지를 거른
  수가 41 → 38 로 준다. CPU 방식에서는 0.83 쯤으로 올리면 41개를 거르고 연기 탐지의 95% 를
  남긴다. 이 문턱은 같은 177개에서 고른 값이라 다른 사진으로 확인해야 한다
- **CPU 에서는 검증기가 병목이다.** 스레드 4개에서 한 번에 11.9초이고 탐지마다 한 번씩 돈다.
  탐지 하나만 검증해도 목표 10초를 넘는다. 사진 한 장에 탐지가 여럿이면 그만큼 곱해진다.
  검증기 조각을 448px 에서 줄이면 빨라지지만 정확도가 유지되는지는 재지 않았다

## 한계

- 시간은 탐지 조각 12개, 사진 5장으로 한 번 잰 값이다. 개발 노트북 값이고 메모리 8GB 상한은
  걸지 않았다
- 오래 돌렸을 때 메모리가 느는 것(7B 16.3GB)은 원인을 확인하지 않았다. 3B 도 느는지 모른다
- 3B 의 사진 전체 수치(48/70)가 `docs/generation_methods.md` 의 GPU 값(51/70)과 다르다. 실행
  방식과 양자화, 질문 항목 수(3개와 5개)가 다르다. 이 문서 안에서는 두 모델의 조건이 같다
- 다른 과제(밑동 고르기, 불꽃, 굴뚝연기 판단, 장소를 섞은 150장)는 7B 로 돌리지 않았다
- 7B 를 양자화 없이 돌린 값은 없다. 4bit 끼리의 비교다
- 평가셋 100장, 장소 두 곳이다
