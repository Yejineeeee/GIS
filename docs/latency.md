# 알람 지연과 설명 지연 측정 (WBS 7.4)

드론처럼 정해진 간격으로 사진이 들어올 때, 관제 요원이 대시보드에서 얼마나 기다리는지 잰다.

```
사진 생김 ──(알람 지연)──▶ 대시보드에 알람 ──(설명 지연)──▶ 대시보드에 설명
```

담당: 박서연 / 상태: 완료 (11/28)

7.3(`docs/device_measure.md`)은 사진을 쉬지 않고 몰아 넣어 기기가 버티는지 봤다. 7.4 는 실제 속도로 넣는다.
그래서 7.3 에서 안 보이던 문제(갱신 때문에 설명이 계속 버려짐)가 드러났고, 고친 뒤 다시 쟀다.

## 방법

`tools/measure_latency.py`

1. `run.py --watch` 를 띄우고, 같은 결과 폴더로 대시보드 서버를 띄운다
2. 자곡동 신고 시나리오 38장(`sim/frames_scenario`)을 **1.5초 ±0.3초** 간격으로 한 장씩 지켜보는 폴더에 넣는다
   (시뮬레이터 대신. 간격을 흔드는 것은 실제 드론도 일정하지 않고, 화면 1초 주기와 박자가 맞물리지 않게 하려는 것)
3. 그동안 두 곳을 지켜본다
   - `alerts.jsonl`: 0.05초마다 읽어 알람이 **파일에 나온** 시각
   - 대시보드 `/api/alerts`: 브라우저와 같이 1초마다 읽어 알람과 설명이 **화면에 뜬** 시각
4. 탐지 번호로 그 사진을 넣은 시각과 이어 지연을 낸다

```bash
# 알람 지연 (VLM 없이)
python tools/measure_latency.py --report results/latency_fake.md -- \
    --weights best.pt --geo-dir data/geo_jagok --sim-terrain sim/terrain_jagok3d.json --vlm fake

# 설명 지연까지 (llama-server 를 잴 때마다 새로 띄운다. 같은 사진의 이미지 캐시가 남으면 거짓으로 빨라진다)
python tools/measure_latency.py --report results/latency_gguf.md -- \
    --weights best.pt --geo-dir data/geo_jagok --sim-terrain sim/terrain_jagok3d.json --vlm gguf
```

- 기기: 박서연 노트북(Core Ultra 7 255U, WSL2), run.py 는 4코어에 묶음, llama-server(Qwen2.5-VL-3B Q4_K_M) `-t 4` 같은 기기
- 알람 1개가 드론이 다가가며 6번 갱신된다(판 7개). "판" = 새 알람이나 갱신마다 하나

## 결과

| 구간 (중앙값 / 최대) | VLM 없음 (fake) | VLM, 고치기 전 | **VLM, 고친 뒤** |
|---|---|---|---|
| 사진 → 탐지 끝 | 0.35 / 0.44초 | 0.83 / 2.96초 | 0.66 / 1.97초 |
| 사진 → 알람 (파일) | 0.40 / 0.51초 | 0.96 / 3.05초 | 0.77 / 2.04초 |
| **사진 → 알람 (화면)** | 0.64 / 1.39초 | 1.69 / 3.01초 | **1.31 / 2.54초** |
| **사진 → 첫 설명 (화면)** | 0.64초 | **83.7초** | **23.7초** |
| 설명이 붙은 판 | 7 / 7 | **1 / 7** | **6 / 7** |
| 갱신된 판: 알람 → 설명 (파일) | 0.10초 | (버려짐) | **0.00초** (중앙값) |
| 사진 → 설명 (화면, 붙은 판) | 0.65초 | 31.0초 (1개) | 1.39 / 2.64초 |

- **알람 지연: 화면에 1~3초.** 화면은 1초마다 새로 읽으므로 파일에 나온 뒤 0~1초가 더해진다. VLM 이 같은 4코어를 쓰면 탐지가 0.35초 → 0.7초로 느려지지만 사진 간격(1.5초)보다 짧다
- **설명 지연 (고치기 전): 첫 설명 83.7초.** 7개 판 중 마지막 하나에만 설명이 붙었다
- **설명 지연 (고친 뒤): 첫 설명 23.7초, 그 뒤 갱신은 알람과 함께.** 첫 설명은 검증(약 11초) + VLM 관찰(약 10초)이다

### 고치기 전에 설명이 83.7초 걸린 이유

알람이 3~6초마다 갱신되는데 설명 하나에 검증 11초 + 설명 10초가 걸렸다. 갱신마다 설명을 새로 만들었고, 다 만들 즈음엔
위치가 또 바뀌어 옛 위치의 설명을 버렸다(`Describer._stale`). 드론이 다가가는 동안은 화면에 계속 "설명 생성 중"이고,
갱신이 멈춘 뒤에야 마지막 위치 설명이 붙었다. 7.3 처럼 사진을 몰아 넣으면 갱신이 몇 초 안에 끝나 이 문제가 작게 보였다(26초).

### 고친 것 (`src/pipeline/alert.py`, `run.py`)

설명 문장은 **VLM 이 본 것**(연기 색, 퍼짐, 불꽃)과 **지도 계산 결과**(용도, 반경, 건물, 경사)를 템플릿이 합쳐 만든다.
같은 연기라면 VLM 이 본 것은 갱신돼도 그대로이고, 바뀌는 것은 지도 계산 결과뿐이다.

- 사건(alert_id)마다 VLM 관찰을 한 번만 받아 둔다(`Describer.obs`). 갱신된 판은 그 관찰로 문장만 다시 만든다(수 ms)
- VLM 을 부르는 동안 갱신되면 버리지 않고 **지금 판**에 문장을 만들어 낸다
- 설명이 검증보다 먼저 붙으면, 검증 결과가 왔을 때 문장을 다시 만든다(`check_update`). "(영상 검증 통과)"가 빠지지 않는다
- 갱신된 판의 VLM 관찰은 다시 받지 않는다. 드론이 다가가며 더 잘 보이게 된 연기를 다시 보지는 않는다(필요하면 향후 과제)

확인: 자곡동 시나리오로 `--vlm fake`, `--sync`, `--no-update`, `--vlm none`, 검증 미통과(P 0.3, 위험도 확인 필요)
모두 형식 검사 통과, `python src/vlm/risk.py` 통과. 고친 뒤 마지막 알람 문장에 "(영상 검증 통과)"와 위험도가 들어감.

### 한 번 크게 느려진 측정

고친 직후 연달아 잰 한 번은 탐지가 사진 간격을 못 따라가 사진 → 탐지 끝이 중앙값 9.7초(최대 20.8초)까지 밀렸다.
같은 코드로 충전기를 꽂고 쉬었다가 다시 재니 0.66초였다. 노트북 CPU 가 느려진 것(발열, 전원)으로 본다.
탐지(0.7초)와 사진 간격(1.5초)의 여유가 2배뿐이라, 기기가 느려지면 알람이 밀릴 수 있다는 뜻이기도 하다.
줄이 쌓이면 최신 사진만 처리하기, llama-server 와 탐지의 코어 나누기를 대책으로 둔다(아래).

## 판단

## 남은 것

- 첫 설명 10초: 검증과 VLM 관찰이 차례로 21초쯤 걸린다. `docs/device_measure.md` "판단"의 1~3(검증 조각 축소 등)과 같이 본다 (4.7 담당과 상의)
- 기기가 느려질 때 알람이 밀리지 않게: 줄이 쌓이면 최신 사진만 처리하는 옵션, 코어 나누기 실험
- 실제 시뮬레이터(V-World, 장 간격 2~5초)로 같은 측정
