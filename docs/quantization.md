# 양자화 설정

경량 VLM을 4GB 노트북에서 돌리기 위해 양자화가 필요하다. 어떤 설정을 쓸지
숫자로 정했다.

담당: 이예진 / 상태: 최종 모델(Qwen2.5-VL-3B)로 재측정 완료 (WBS 7.1, 7.2)

## 1차 측정: InternVL3-2B (7.1)

모델을 고르기 전에 잰 것이다. 설정별 차이를 보려는 것이었고, 최종 모델로 다시 잰
결과는 다음 절에 있다.

InternVL3-2B, 이미지 타일 6개, 새 토큰 120개 상한, 같은 프롬프트.
개발 노트북은 RTX 3050 4GB이고 실측 여유는 3.23GB다.

| 설정 | 가중치 | 최대 VRAM | 생성 | 초당 토큰 |
|---|---|---|---|---|
| fp16 (양자화 없음) | 3.23GB | 4.42GB | 97.1초 | 0.4 |
| 8bit | 2.83GB | 2.93GB | 19.8초 | 2.0 |
| 4bit fp4 | 1.97GB | 2.26GB | 10.2초 | 6.5 |
| 4bit nf4 | 1.97GB | 2.26GB | 9.6초 | 5.2 |
| 4bit nf4 + 이중 양자화 | 1.90GB | 2.19GB | 8.7초 | 5.8 |

측정값은 `results/quant_compare.csv`에 있다.

## 2차 측정: Qwen2.5-VL-3B (7.2)

최종 모델로 다시 쟀다. 평가셋 사진 1장(흑색연기), 입력 상한 768x768, 새 토큰 120개
상한, 조건 A 프롬프트, 그리디 디코딩이다. 입력 상한은 다른 실행기와 같게 맞췄다.

| 설정 | 가중치 | 최대 VRAM | 로딩 | 생성 | 초당 토큰 | 형식 |
|---|---|---|---|---|---|---|
| fp16 | 3.23GB | 7.32GB | 31초 | 219.8초 | 0.4 | 예 |
| 8bit | 3.23GB | 4.07GB | 36초 | 924.9초 | 0.1 | 예 |
| 4bit fp4 | 2.51GB | 2.66GB | 26초 | 9.4초 | 6.7 | 아니오 |
| 4bit nf4 | 2.51GB | 2.66GB | 24초 | 12.7초 | 5.6 | 예 |
| 4bit nf4 + 이중 양자화 | 2.37GB | 2.51GB | 22초 | 6.9초 | 8.4 | 예 |
| 4bit nf4 + 이중 양자화, bf16 계산 | 2.37GB | 2.51GB | 19초 | 6.5초 | 8.9 | 예 |

측정값은 `results/quant_compare_qwen.csv`에 있다.

### fp16과 8bit는 이 카드에서 안 된다

2B에서 3B로 오면서 선을 넘었다. fp16은 최대 7.32GB, 8bit는 4.07GB를 썼고 카드는
4GB다. 넘긴 만큼 시스템 메모리로 오가느라 8bit가 924.9초, 즉 15분이 걸렸다.
4bit의 134배다.

1차 측정에서 8bit는 19.8초였다. 모델이 커지면 같은 설정이라도 결론이 뒤집힌다.

### fp4가 형식을 깼다

같은 사진에서 fp4만 출력 앞머리에 쓰레기 토큰이 붙어 JSON이 깨졌다. 문장 자체는
멀쩡했다.

```
```json
{
-
-{"Aerial view: {""description": "산불지역에서 연기가 관측된다. ..."
```

fp4 3회, nf4 3회를 돌려 fp4는 세 번 다 같은 자리에서 깨졌고 nf4는 세 번 다
깨끗했다. 다만 그리디 디코딩이라 같은 사진이면 결과가 결정적이므로, 반복은
우연이 아니라는 것만 보여 준다. **사진 1장 기준이고 fp4가 일반적으로 형식을
깬다고 말할 근거는 아직 없다.**

### bf16 계산은 비용이 없다

가중치와 최대 VRAM이 fp16 계산과 같고 생성은 오히려 0.4초 빨랐다.

계산 dtype이 fp16이면 어떤 입력에서 모델 출력 전체가 NaN이 된다
(`docs/generation_methods.md`). bf16으로 바꾸면 사라지는데, 이 표가 그 교체에
메모리나 속도를 치르지 않는다는 것을 보여 준다.

## 결정

**4bit nf4에 이중 양자화를 켜고, 계산 dtype은 bf16을 쓴다.**

1. 메모리가 가장 적다. 2.37GB로 fp16의 73% 수준이다.
2. 가장 빠르다. fp16보다 34배, 8bit보다 142배 빠르다.
3. 이중 양자화는 0.14GB를 더 줄이면서 속도도 떨어지지 않았다.
4. bf16 계산은 메모리와 속도를 치르지 않으면서 NaN 문제를 없앤다.

1차 측정에서는 nf4와 fp4가 메모리와 속도가 거의 같아, nf4를 고른 근거가 일반적으로
품질이 낫다고 알려져 있다는 것뿐이었다. 2차 측정에서 fp4만 형식을 깨는 것을 봤다.
사진 1장 기준이지만 nf4를 유지할 이유는 생겼다.

## fp16이 느린 이유

fp16은 최대 4.42GB를 썼는데 여유가 3.23GB였다. 그런데도 메모리 부족 오류가 나지
않았다. Windows가 모자란 만큼 시스템 메모리로 넘겼기 때문이다.

오류가 없으니 잘 돌아가는 것처럼 보이지만 초당 0.4토큰이다. 4bit의 13분의 1이다.
**양자화 설정을 고를 때 올라가는지로 판단하면 안 된다.** 처리 시간으로 판단해야
한다.

같은 함정이 분할 모델 학습에서도 나타났다. `docs/train_setup.md`의 배치 크기 항목에
적어 두었다.

## 8bit가 느린 이유

8bit는 2.93GB로 여유 안에 들어갔는데도 초당 2.0토큰이었다. 4bit의 3분의 1이다.
메모리가 넘친 것이 아니므로 시스템 메모리 문제는 아니고, bitsandbytes의 int8
연산이 4bit보다 느리게 도는 것으로 보인다. 원인을 더 파지는 않았다. 우리에게는
4bit가 메모리와 속도 모두 낫다는 결론이면 충분하다.

## 환경

Windows에서 별도 작업 없이 설치된다. 예전에는 Windows용 바이너리를 따로 구해야
했으나 지금은 필요 없다.

```
pip install bitsandbytes
```

확인한 버전은 bitsandbytes 0.50.2, transformers 5.17.0, torch 2.6.0+cu124다.

## 쓰는 법

```python
from transformers import BitsAndBytesConfig
import torch

quant = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.bfloat16,
    bnb_4bit_use_double_quant=True,
)
```

다시 재려면 `python tools/quant_compare.py`. 설정마다 프로세스를 새로 띄운다.
한 프로세스에서 이어서 재면 앞 모델이 완전히 비워지지 않아 값이 섞인다.

## 남은 것

- fp4와 nf4의 형식 차이를 사진 여러 장으로 다시 본다. 지금은 1장 기준이다.
- 현장 기기 기준은 CPU 4코어다. 4bit 양자화는 GPU를 전제로 한 방식이므로,
  CPU에서는 다른 방법이 필요하다. 12주차 작업에서 확인한다.
