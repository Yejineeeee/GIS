# 설명 입력 조합별 CPU 시간

GPU 에서 고른 개선(전체 사진과 탐지 조각을 함께 넣기, 불꽃을 따로 묻기)이 현장 기기 기준인
CPU 4코어에서 목표 10초 안에 드는지 쟀다.

담당: 이예진 / 상태: 측정 완료. 기준 환경(8GB 제한, 박서연 7.3)에서 다시 재야 한다

## 방법

`tools/measure_inputs_cpu.py`. `docs/vlm_speed.md`(7.2)와 같은 방식이다.

- llama-server(llama.cpp b12374, 윈도우 CPU 빌드), Qwen2.5-VL-3B Q4_K_M, 스레드 4
- 평가셋에서 탐지가 있는 연기 사진 6장, 조건마다 2번. 조건마다 슬롯 캐시를 비운다
- 조각은 탐지 상자를 모두 감싼 상자 그대로(여백 1배, 최소 96px), 긴 변 1024 까지
- 개발 노트북(Core Ultra 7 155H), 전원 연결, 다른 실험 없이 혼자 돌렸다. 메모리 상한은 걸지 않았다

```
python tools/measure_inputs_cpu.py --eval data/eval_100 --dets runs/verify_real/verify_real.jsonl \
    --out results/inputs_cpu.csv
```

## 결과

| 조건 | 입력 토큰 | 1장 처리 (중앙값) | 최소 ~ 최대 |
|---|---|---|---|
| 탐지 조각만, 세 항목 | 96 ~ 935 | 28.1초 | 2.6 ~ 54.6초 |
| 위 설명 직후 같은 조각에 불꽃 질문 | 25 (사진은 재사용) | **0.7초** | 0.5 ~ 0.8초 |
| 불꽃 질문만 따로 | 53 ~ 892 | 25.3초 | 1.5 ~ 48.9초 |
| 줄인 전체(긴 변 448) + 조각 | 268 ~ 1107 | 37.1초 | 11.9 ~ 61.0초 |
| 사진 전체만 | 861 | 48.0초 | 44.0 ~ 53.1초 |
| 사진 전체 + 조각 | 901 ~ 1740 | 75.1초 | 45.4 ~ 98.0초 |

서버 메모리는 최대 5.19GB 였다. 두 번의 반복은 서로 2~4초 안에서 같았다.

- **시간은 입력 토큰 수에 비례한다.** 토큰 하나에 약 0.053초다. 출력(34토큰)은 거의 영향이 없다
- **불꽃 질문은 설명 뒤에 덧붙이면 0.7초다.** 같은 사진을 다시 처리하지 않기 때문이다.
  따로 물으면 조각을 처음부터 처리해 25초가 든다. 설명과 같은 조각으로, 바로 이어서 물어야 한다
- **전체 사진을 넣는 조합은 모두 목표를 넘는다.** 전체만 48초, 전체 + 조각 75초, 전체를 줄여도 37초다.
  GPU 에서 연기 인식을 64% 에서 81% 로 올린 전체 + 조각 입력(`docs/vlm_crop_views.md`)은 CPU 에서 쓸 수 없다
- **조각만 넣어도 조각이 크면 목표를 넘는다.** 96토큰(108x96)은 3초, 935토큰(1024x642)은 55초다.
  10초 안에 들려면 입력이 약 180토큰, 조각으로는 긴 변 360 안팎이어야 한다

## 조각의 긴 변을 360, 300 으로 줄이면

위 결과에서 조각을 줄이면 10초 안에 들 것으로 보여, 줄였을 때의 시간과 연기 인식을 따로 쟀다.

### CPU 시간

위와 같은 방식으로 조각의 긴 변 상한만 바꿔 쟀다(`--crop-px`). 탐지가 있는 연기 사진 12장, 전원 연결.
360 은 세 번, 300 은 두 번 쟀다. 360 과 300 을 이어서 잴 때는 순서를 바꿔 한 번 더 쟀다.

```
python tools/measure_inputs_cpu.py --eval data/eval_100 --dets runs/verify_real/verify_real.jsonl \
    --conds crop --crop-px 360 --n 12 --runs 1 --out results/inputs_cpu_px360.csv
```

결과 파일은 `results/inputs_cpu_px360.csv`(360 만), `results/inputs_cpu_px_run1.csv`(1024 → 360 → 300 순),
`results/inputs_cpu_px_run2.csv`(300 → 360 순)이다.

| 조각 긴 변 | 입력 토큰 | 1장 처리 (중앙값) | 최소 ~ 최대 | 10초 넘은 것 |
|---|---|---|---|---|
| 1024 (3장) | 484 ~ 935 | 27.9초 | 21.3 ~ 46.0초 | 3장 중 3장 |
| 360 | 96 ~ 240 | **9.3초, 9.2초, 9.4초** | 4.7 ~ 12.0초 | 12장 중 4장, 3장, 3장 |
| 300 | 96 ~ 194 | 9.6초, 7.7초 | 4.7 ~ 12.6초 | 12장 중 4장, 1장 |

- **긴 변 360 이면 중앙값이 10초 안에 든다.** 세 번 재서 9.3초, 9.2초, 9.4초였다. 같은 사진으로 보면
  1024 일 때 46.0초가 9.2초로, 27.9초가 11.5초로 줄었다
- **모든 사진이 10초 안에 드는 것은 아니다.** 줄인 뒤에도 정사각형에 가까운 조각(360x336, 240토큰)은
  11~12초가 걸린다
- **300 은 360 보다 조금 빠르지만 차이가 작고, 측정마다 달랐다.** 360 다음에 재면 9.6초, 먼저 재면
  7.7초였다. 뒤에 잰 쪽이 느려지는 것으로 보아 기기가 달아오른 영향이 섞여 있다
- 전원을 빼고 배터리로 재면 같은 360 이 13.7초(7.3 ~ 17.1초)였다. 전원 상태가 결과를 크게 바꾼다

### 연기 인식 (GPU, 평가셋 100장)

`tools/vlm_crop_views.py run B --crop-px 360` 으로, 조각만 주는 조건(B)에서 긴 변만 바꿨다.
조각은 정답 라벨 상자를 1.5배 넓힌 것이다(`docs/vlm_crop_views.md`).

| 항목 | 사진 전체 | 조각 768 | 조각 360 | 조각 300 |
|---|---|---|---|---|
| 연기 사진을 연기라고 함 | 45/70 | 64/70 | **67/70** | 66/70 |
| 연기 아닌 사진을 아니라고 함 | 17/30 | 10/30 | 6/30 | 5/30 |
| 　구름 | 14/15 | 7/15 | 4/15 | 3/15 |
| 　굴뚝연기 | 3/15 | 3/15 | 2/15 | 2/15 |
| 연기 면적 0.5% 미만 | 1/17 | 15/17 | 15/17 | 15/17 |
| 입력 토큰 (중앙값) | - | 352 | 209 | 205 |

- **줄여도 연기를 놓치지 않는다.** 360 에서 67/70, 300 에서 66/70 이다. 가장 작은 연기(면적 0.5% 미만)도
  15/17 로 같다
- **연기가 아닌 것을 거르는 힘은 더 약해진다.** 구름을 아니라고 한 수가 7장에서 4장, 3장으로 준다.
  조각이 흐려질수록 "연기"라고 답하는 쪽으로 기운다. 768 과 360 에서 답이 달라진 9장 중 8장이
  "연기 없음"에서 "연기 있음"으로 바뀐 것이다
- CPU 에서 잰 12장(연기 사진)은 360, 300 모두 11장을 연기라고 했다. 놓친 한 장은 가로로 긴 탐지
  상자가 360x64 로 줄어든 조각이다

### 정리

조각의 긴 변을 360 으로 두면 설명 단계는 연기 인식을 잃지 않고 CPU 에서 중앙값 9초쯤에 끝난다.
300 까지 줄여도 얻는 것이 작아서 360 을 권한다. 연기가 아닌 것을 거르는 일은 설명 단계에 기대할 수
없고, 조각에 예/아니오만 묻는 검증기(`docs/vlm_compare.md`)가 맡는다.

## 7.2 의 9.2초와 다른 이유

`docs/vlm_speed.md` 의 9.2초는 입력 188토큰일 때 값이다. 그때 쓴 6장은 탐지 상자가 작았다.
이번 6장은 탐지 상자를 모두 감싸면 화면의 큰 부분을 차지하는 사진이 섞여 있다. 토큰당 시간도
이번이 더 길다(7.2 는 약 0.040초, 이번은 0.053초). 실행 파일 버전이 다르고, 배터리가 낮은
상태에서 충전하며 쟀다. 절대값보다 조건 사이의 비율을 본다.

## 파이프라인에 주는 뜻

1. 지금 `src/pipeline/vlm_client.py` 의 `observe` 는 사진 전체를 넣는다. CPU 에서는 한 장에 48초다.
   현장 기기에서 10초를 맞추려면 탐지 조각을 넣고 크기 상한을 둬야 한다
2. 조각의 긴 변 상한은 360 을 권한다. 연기 인식은 유지되고(67/70) CPU 에서 중앙값 9초쯤이다.
   다만 큰 조각은 11~12초가 걸린다
3. 불꽃 질문은 설명과 같은 조각에 이어서 물으면 비용이 거의 없다. CPU 에서도 넣을 수 있는 개선이다

## 한계

- 사진 6장, 2번 반복이다. 개발 노트북 값이고 메모리 8GB 제한을 걸지 않았다
- 검증기(탐지마다 한 번)와 설명이 같은 CPU 를 쓰는 경우의 대기 시간은 재지 않았다
- 조각 크기별 시간은 12장, 두세 번 반복이다. 300 은 측정 순서에 따라 2초쯤 달랐다
- 조각 크기별 연기 인식은 평가셋 v1(6.2 사람 검토 전)로 잰 값이다. 확정본으로는 다시 재지 않았다
- 조각 크기별 연기 인식은 GPU(4bit nf4)에서 잰 값이다. CPU 실행 방식(GGUF Q4_K_M)으로는 12장만 봤다
- 연기 인식은 정답 라벨로 자른 조각, CPU 시간은 탐지 상자로 자른 조각이라 조각을 만드는 법이 다르다
- 줄인 조각으로 검증기(예/아니오, 0.7 기준)의 정확도가 유지되는지는 재지 않았다
