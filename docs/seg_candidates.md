# 분할 모델 후보 비교

연기 영역을 찾는 분할 모델을 고른다. 발표할 처리 시간은 현장 기기 기준인 CPU
4코어에서 잰 값이다. GPU 값은 개발 중 반복 실행 속도를 보기 위한 참고다.

담당: 이예진 / 상태: 완료. 속도, 정확도, 의미 분할 비교까지 끝났고 YOLO11n-seg를 그대로 쓴다

## 측정 결과

입력 640, 이미지 1024x768, 중앙값 9회.

| 모델 | 파라미터 | 연산량 | 파일 | CPU 4코어 | GPU |
|---|---|---|---|---|---|
| YOLO11n-seg | 2.88M | 10.0 GFLOPs | 5.9MB | 82ms | 18ms |
| YOLOv8n-seg | 3.41M | 12.1 GFLOPs | 6.7MB | 107ms | 14ms |
| YOLO11s-seg | 10.11M | 33.4 GFLOPs | 19.7MB | 141ms | 21ms |
| YOLOv8s-seg | 11.82M | 40.3 GFLOPs | 22.8MB | 230ms | 15ms |
| YOLO11m-seg | 22.42M | 114.0 GFLOPs | 43.3MB | 519ms | 36ms |

측정값은 `results/seg_model_compare.csv`에 있다. 다시 재려면
`python tools/compare_seg_models.py 이미지경로`.

## 측정 방법

처음 잰 값은 쓸 수 없었다. 22M 모델이 2.9M 모델보다 빠르게 나왔다. 원인은 두
가지였다. 측정 중간에 가중치를 내려받았고, 이미지를 매번 디스크에서 읽었다.

고친 방법
- 가중치를 모두 먼저 내려받은 뒤에 잰다
- 이미지를 미리 메모리에 올린다
- 추론 시간만 쓰고 전처리와 후처리는 따로 적는다
- 장치마다 모델을 새로 만들고 장치별로 몰아서 잰다

고친 뒤에는 연산량이 커질수록 시간이 늘어나는 순서가 맞았다.

## 선정

**YOLO11n-seg를 1순위로 한다.**

1. CPU 4코어에서 82ms로 가장 빠르다. 후보 중 유일하게 100ms 아래다.
2. 파일이 5.9MB로 가장 작다.
3. 같은 세대 s 모델보다 연산량이 3분의 1인데 CPU 시간은 40% 수준이다.

GPU만 보면 YOLOv8n이 더 빠르지만, 우리가 발표할 조건은 CPU다. GPU 차이 4ms는
현장 기기와 무관하다.

## 정확도 비교 결과

실제 데이터 1,260장으로 n과 s를 각각 학습했다. 자세한 것은
`docs/train_results.md`에 있다.

| | yolo11n @960 | yolo11s @640 |
|---|---|---|
| 분할 mAP50 | 0.559 | 0.510 |
| 파라미터 | 2.88M | 10.11M |

헛탐지율을 맞춰 놓고 작은 연기 탐지율을 비교해도 모든 지점에서 n이 앞섰다.

| 배경 헛탐지 | yolo11n @960 | yolo11s @640 |
|---|---|---|
| 약 2% | 73% | 54% |
| 약 11% | 96% | 91% |
| 약 19% | 98% | 96% |

**n이 밀리지 않았으므로 바꾸지 않는다.** 1,260장으로 10M 파라미터를 채우기에는
데이터가 모자란 것으로 본다. 데이터가 크게 늘면 다시 볼 일이다.

## 개체 분할과 의미 분할

개체 분할은 사물을 하나씩 세는 방식인데 연기는 셀 수 있는 사물이 아니다. 실제로
학습한 모델이 연기 덩어리 하나를 세 조각으로 쪼개서 낸 경우가 있었다. 픽셀마다
연기인지만 정하는 의미 분할이 더 맞을 수 있어 SegFormer-B0을 비교했다. 결과는
아래에 있다.

## 의미 분할 비교 (SegFormer-B0)

연기는 경계가 흐릿해 개체로 세기 어렵다. 그래서 픽셀마다 분류하는 방식이 더 나은지
같은 데이터로 재 봤다.

### 먼저 CPU 속도

선정 기준이 속도였으므로 학습 전에 추론 시간부터 쟀다. 조건은
`compare_seg_models.py`와 같다. CPU 4코어, 워밍업 3회 뒤 9회 중앙값.

| 모델 | 640px | 960px |
|---|---|---|
| YOLO11n-seg | 82ms | 133ms |
| SegFormer-B0 | 340ms | 923ms |

640에서 4.1배 느리다. 파라미터는 3.71M으로 YOLO11n-seg의 2.88M과 비슷한데도 그렇다.
트랜스포머 구조가 CPU에서 불리하다.

처음에는 이것만 보고 학습할 필요가 없다고 판단했으나, 문서 어디에도 처리 시간
목표가 없다는 것을 확인했다. 100ms는 모델을 고를 때 적어 둔 관찰이지 기준이 아니다.
실제로 필요한 속도는 프레임 간격으로 정해지는데 그 값이 정해져 있지 않다. 그래서
학습까지 진행했다. 처리 시간 목표를 정하는 것은 `device_spec.md`에 남은 과제다.

### 학습과 결과

1,260장을 같은 분할로 쓰고, YOLO 폴리곤 라벨을 마스크 PNG로 바꿔 학습했다
(`tools/make_masks.py`, `tools/train_segformer.py`). 연기 픽셀이 전체의 몇
퍼센트뿐이라 손실에 8배 가중치를 줬다.

연기 IoU가 9에폭부터 0.54에서 0.56 사이를 오가 20에폭에서 멈췄다. 손실은 계속
떨어지는데 검증 IoU가 오르지 않았다.

| | YOLO11n-seg @960 | SegFormer-B0 @640 |
|---|---|---|
| 작은 연기 (화면 0.2% 미만) | 41/53 (77%) | 30/53 (57%) |
| 큰 연기 | 133/137 (97%) | 133/137 (97%) |
| 배경 헛탐지 | 2/62 (3%) | 7/62 (11%) |
| 연기 픽셀 IoU | 0.5861 | 0.5713 |
| CPU 4코어 추론 | 133ms | 340ms |

두 모델의 출력 형태가 달라 YOLO 마스크를 한 장으로 합쳐 픽셀 단위로 맞췄다. 입력은
둘 다 원본 사진을 주고 줄이는 것은 각자에게 맡겼다. 처음에 640으로 미리 줄여서
주었더니 YOLO가 불리해져 IoU가 0.4872로 나왔다. 한쪽 크기로 맞춰서 주면 안 된다.

**모든 항목에서 YOLO11n-seg가 앞서거나 같다.** 마스크 품질이 더 나을 것이라는
예상도 맞지 않았다.

### 조건이 같지 않다

| | YOLO | SegFormer |
|---|---|---|
| 입력 크기 | 960 | 640 |
| 증강 | mosaic 포함 | 좌우 뒤집기만 |
| 에폭 | 100 | 20 |

SegFormer를 960으로 돌리려 했으나 4GB에 들어가지 않았다. 손실을 계산할 때 출력을
입력 크기로 되돌리는데, SegFormer는 보통 1/4 해상도에서 손실을 계산한다. 그대로
두고 640으로 내렸다.

작은 연기 격차(77% 대 57%)는 해상도 탓일 가능성이 크다. YOLO도 640에서는 62%였다
(`docs/train_results.md`). 960으로 돌릴 수 있었다면 비슷해졌을 수 있다.

그래서 결론은 의미 분할이 더 나쁘다는 것이 아니라, **4GB 제약 아래에서는
YOLO11n-seg가 낫다**는 것이다. 메모리가 넉넉한 기기라면 다시 볼 일이다.

## 다루지 않은 대안

RTMDet-Ins-tiny는 Apache 2.0이라 라이선스가 자유롭다. mmdetection 설치가
Windows에서 까다로워 재지 않았다. 라이선스 때문에 바꿔야 하는 상황이 오면 이쪽을
본다. 다만 RTMDet도 YOLO와 같은 개체 분할이라 방식이 달라지지 않는다.

U-Net 계열도 재지 않았다. SegFormer보다 구조가 단순해 CPU에서 더 빠를 수 있다.
의미 분할을 다시 본다면 이쪽이 먼저다.

## 라이선스

ultralytics는 AGPL-3.0이다. 수업 과제와 연구 목적에는 문제가 없으나 상업적으로
쓰려면 별도 허락이 필요하다. Qwen2.5-VL-3B도 같은 상황이므로, 최종 결과물을
상업적으로 쓸 수 없다는 점을 한곳에 적어 둔다.
