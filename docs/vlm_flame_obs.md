# VLM 이 본 불꽃과 굴뚝을 해설과 위험도에 연결

해설 문장은 판정과 계산값으로 만들고, VLM 은 연기인지 확인하는 데만 썼다. 파이프라인은 설명 단계에서
VLM 에게 사진 관찰(연기 유무, 색, 퍼짐, 불꽃, 지형)을 JSON 으로 받았지만, 늘 같은 답보다 못해서
문장에는 쓰지 않았다(`docs/vlm_compare.md`). 불꽃은 위험도 규칙에 들어가지만 이 방식으로는 불꽃 19장 중
한 장도 "있다"고 하지 않아 사실상 쓰이지 않았다.

불꽃만 같은 조각에 따로 묻도록 바꿔, VLM 이 본 것이 해설과 위험도를 실제로 바꾸게 했다.
11/28 에 굴뚝도 연결했다(아래 "굴뚝 연결"). 불꽃은 위험도를 올리고, 굴뚝은 내린다.

담당: 이예진 / 상태: 연결과 측정 완료(11/26). **소형 GPU 기기 구성(qwen, nf4)에서만 켠다.** CPU 하한 구성(gguf)에서는
헛말이 많아 끈다(아래 "현장 구성(gguf)으로 다시 잰 불꽃 57장")

## 바꾼 것

| 파일 | 내용 |
|---|---|
| `src/pipeline/vlm_client.py` | `p_yes(image, bbox, prompt)` 로 검증기 계산을 질문만 바꿔 쓸 수 있게 하고, `p_flame` 추가. 질문 "이 사진에 불꽃이 보이는가. 예 또는 아니오로만 답하라.", 문턱 `FLAME_TAU = 0.7`(검증기와 같은 값, 미리 정함). `FLAME_MODES = ("qwen", "fake")` 밖(gguf)에서는 묻지 않는다 |
| `src/pipeline/alert.py` | 설명 단계에서 JSON 관찰보다 먼저 알람의 탐지 조각에 불꽃을 따로 묻고(검증기가 방금 본 조각이면 llama-server 캐시를 쓴다) `observed.flame_visible` 을 그 답으로 바꾼다. 확률과 시간은 `debug.jsonl` 의 `p_flame`, `flame_ms` 에 남긴다. 묻지 않은 모드에서는 예전처럼 구조화 질문의 답을 쓴다 |
| `src/vlm/templates.py` | 불꽃 문장을 "불꽃도 함께 보인다" → "불꽃으로 보이는 것이 있다"로 낮췄다(열에 둘은 틀리므로) |

위험도 규칙(`src/vlm/risk.py`)은 그대로다. 불꽃이 보이면 높음이고(4번 줄), 위치가 미확정이면 불꽃이 보여도
확인 필요다(3번 줄). 알람 형식(`docs/schema.md`)도 그대로다. 조각과 계산은 검증기와 같아 gguf 모드에서도 같은 길로 묻는다.

## 측정: 실제 탐지 조각에서

`tools/flame_detcrop.py`. `tools/flame_eval.py` 와 같은 사진 57장(학습용 1,260장 중 화염 라벨이 있는 연기 사진 19장 전부,
같은 카메라·영상의 화염 라벨 없는 연기 사진 38장)에서, 탐지기가 낸 박스 중 검증기를 통과한 conf 1등을 파이프라인처럼 골라 물었다.

| 조각 | AUC | 문턱 0.7: 불꽃 19장 중 "있다" | 없음 38장 중 "있다" |
|---|---|---|---|
| 구조화 질문 (전에 쓰던 방식) | | 0 | 0 |
| 연기 라벨 박스 (`flame_eval.py`) | 0.86 | 10 | 1 |
| **실제 탐지 박스 (지금 파이프라인)** | **0.83** | **10** | **3** |

- 불꽃의 절반(10/19)을 잡는다. "있다"고 한 13번 중 10번이 맞다(77%)
- 헛말 3장은 모두 같은 카메라(RD030033)의 다른 영상이다. 불꽃 사진과 같은 영상은 아니다
- 불꽃은 화면의 0.007%(중앙값)로 작다. 19장 중 18장에서 불꽃이 조각 안에 들어 있었다
- 질문 한 번에 GPU(RTX 3050)에서 1.1초(중앙값)

참고(문턱을 이 57장으로 고르면 낙관적이다): 문턱 0.5 에서 14/19, 헛말 8/38. 0.9 에서 4/19, 헛말 0/38.

## 파이프라인 실행 확인

자곡동 시뮬레이터 프레임 32장에 `run.py --vlm qwen --sync` 로 돌렸다. 알람 5개 모두 설명이 붙었고
불꽃 확률은 0.11 ~ 0.41 로 모두 "없음"이었다(시뮬레이터 연기에는 불꽃이 없다). 알람 형식 검사 5/5 통과.

불꽃이 "있다"일 때 문장은 이렇게 바뀐다(같은 알람, 확정·자연녹지·건물 없음).

```
불꽃 없음: 연기가 탐지되었다(영상 검증 통과). 자연녹지지역(100%)에서 발생했다. ... 위험도 보통: 반경 안은 자연녹지지역이다.
불꽃 있음: 연기가 탐지되었다(영상 검증 통과). 불꽃으로 보이는 것이 있다. 자연녹지지역(100%)에서 발생했다. ... 위험도 높음: 불꽃이 보인다.
```

## 주의할 점

- 불꽃 사진은 19장뿐이고 탐지기 학습에 쓴 사진이다. 문턱 0.7 은 미리 정했지만 다른 불꽃 사진으로 다시 재야 한다
- 같은 영상의 "화염 라벨 없음" 사진에 라벨만 빠진 불꽃이 있을 수 있다
- CPU 4코어(gguf)에서 질문 한 번이 얼마나 걸리는지 아직 재지 않았다. 검증기 질문과 같은 조각이라
  llama-server 의 프롬프트 캐시가 맞으면 짧겠지만 확인이 필요하다
- (11/28 에 GPU 구성에만 연결했다. 아래 "굴뚝 연결") 굴뚝 판단은 사진 전체를 봐야 맞고(조각에서는 5장 중 2장), CPU 에서 사진 전체는
  40초가 넘는다(`docs/vlm_situation.md`, `docs/inputs_cpu.md`). 소형 GPU 기기에서 켜는 선택지로 남긴다

결과 파일: `results/flame_detcrop.jsonl`

```
python tools/flame_detcrop.py data/yolo_1260 data/yolo_1260_raw_labels runs/smoke_1260_960/weights/best.pt --out runs/flame_detcrop.jsonl
```

## CPU 측정 (현장 기기 구성, 11/26)

`tools/measure_device.py --cores 4 --mem-gb 8` 과 llama-server(Q4_K_M, `-t 4 -c 8192 -np 1`, 잴 때마다 새로 띄움),
`sim/frames_scenario` 38장. 이 노트북 윈도우에서는 `CUDA_VISIBLE_DEVICES` 를 비워도 탐지기가 GPU 를 찾다 멈춰서,
측정 도구는 고치지 않고 감싸는 스크립트로 그 값만 `-1` 로 바꿔 돌렸다. 불꽃 질문은 설명보다 먼저 묻도록 순서를 바꾼 코드다.

| | 불꽃 연결 전 (main) | 불꽃 연결 후 |
|---|---|---|
| 탐지 → 알람 | 0.32초 | 0.35초 |
| 검증기 1번 | 14.8초 | 16.1초 |
| 알람 → 설명 (마지막 갱신) | 54.4초 | **75.0초** |
| 불꽃 질문 1번 | | 0.7초 (첫 설명) / **16.2초** (마지막 설명) |

- 알람은 그대로 1초 안에 나간다. 늘어나는 것은 설명이다
- 불꽃 질문이 검증기가 방금 본 조각과 같으면 llama-server 가 이미지를 다시 계산하지 않아 0.7초다.
  마지막 갱신의 탐지는 검증을 건너뛰고 묶인 것이라 조각을 새로 계산해 16.2초가 걸렸다
- 같은 기기의 main 코드도 이번에는 54.4초였다(서연 11/19 측정 26.0초와 다르다. 기기와 실행 조건 차이로 보이며 따로 확인 필요)

**시뮬레이터 연기에서 헛말이 났다.** 첫 설명에서 불꽃 확률 0.83 으로 "불꽃으로 보이는 것이 있다"가 붙고 위험도가 높음이 됐다.
조각을 직접 보니 건물 위의 흰 연기뿐이고 불꽃은 없다. GPU(nf4)로 자곡동 프레임 32장을 돌렸을 때는 0.11 ~ 0.41 로 모두 없음이었다.
현장 구성(gguf Q4_K_M)은 양자화가 달라 확률이 다를 수 있는데, 57장 측정은 nf4 로만 했다.

## 현장 구성(gguf)으로 다시 잰 불꽃 57장

같은 사진, 같은 탐지 박스에 llama-server(Q4_K_M)로 같은 질문을 했다(`--vlm gguf --boxes`, 결과 `results/flame_detcrop_gguf.jsonl`).

| 모델 | AUC | 문턱 0.7: 불꽃 19장 중 "있다" | 없음 38장 중 "있다" | 문턱 0.9 | 질문 1번 |
|---|---|---|---|---|---|
| nf4 (GPU, transformers) | 0.83 | 10 | 3 | 4 / 0 | 1.1초 (GPU) |
| **Q4_K_M (CPU, llama-server)** | **0.80** | 15 | **12** | 10 / 2 | 8.8초 (8스레드) |

- 두 모델의 확률은 비슷하게 움직이지만(상관 0.85) gguf 쪽이 전체로 높게 나온다. 같은 문턱 0.7 에서 헛말이 3 → 12장(32%)이 된다
- 시뮬레이터 흰 연기를 0.83 으로 본 것도 같은 현상이다
- 문턱 0.9 면 10/19, 헛말 2/38 이지만, 이 57장을 보고 고른 값이라 낙관적이다. 다른 불꽃 사진이 없어 따로 맞출 수 없다

**결론: 불꽃 질문은 nf4(소형 GPU 기기)에서만 미리 정한 문턱 0.7 로 쓸 수 있다.** 현장 하한 구성(CPU, gguf)에서는
미리 정한 문턱으로는 헛말이 많고 설명도 최대 16초 늘어나, 켜려면 gguf 용 문턱을 다른 불꽃 사진으로 따로 정해야 한다.


## 굴뚝 연결 (11/28)

위험도 규칙에는 "굴뚝으로 보이고 반경 안에 건물이 있으면 낮음", "굴뚝으로 보이는데 건물이 없으면 확인 필요" 줄이
있었지만(`src/vlm/risk.py` 1, 2번 줄), 파이프라인이 굴뚝 값을 넘기지 않아 비어 있었다.

| 파일 | 내용 |
|---|---|
| `src/pipeline/vlm_client.py` | `situation()`, `is_chimney()`. 사진 전체(긴 변 1024)에 `tools/vlm_situation.py` 와 같은 넷 중 하나 질문을 하고, 답 토큰 확률에서 "2 굴뚝"이 가장 높으면 굴뚝. `CHIMNEY_MODES = ("qwen", "fake")` |
| `src/pipeline/alert.py` | 설명 단계에서 굴뚝을 묻고, 위험도를 매길 때 넘긴다. 알람 형식의 `observed` 에는 칸이 없어(형식 검사가 정의되지 않은 키를 막는다) 위험도 등급과 근거에만 반영하고, 확률은 `debug.jsonl` 의 `situation` 에 남긴다 |
| `src/vlm/templates.py` | 설명의 위험도 문장도 같은 굴뚝 값으로 매긴다 |

불꽃이 보이면 굴뚝으로 보여도 낮추지 않는다(규칙 그대로).

### 측정

같은 코드로 평가셋 확정본 100장에 물었다(`results/chimney_eval_v2.json`). 11/12 측정(`docs/vlm_situation.md`)은 평가셋 v1 이다.

| 정답 | "굴뚝"이라고 한 사진 |
|---|---|
| 산불 연기 70장 | **0** |
| 굴뚝연기 15장 | **15** |
| 구름 15장 | 1 |

- 질문 한 번에 GPU(RTX 3050)에서 2.6초(중앙값)
- 평가셋의 굴뚝 사진은 모두 같은 공업 지역이다. 장소를 섞은 150장에서는 공장 지대 굴뚝 14/15, 그 밖 1/15 였다.
  그래서 "굴뚝이라고 하면 믿을 만하지만, 굴뚝을 다 찾지는 못한다"로 쓴다. 산불을 굴뚝이라고 한 적은 두 세트 130장 중 0장이다

자곡동 시뮬레이터 프레임 32장을 `run.py --vlm qwen --sync` 로 돌렸다. 알람 5개 모두 "굴뚝 아님"(산불 0.38 ~ 0.61, 굴뚝 0.25 ~ 0.33),
설명 5/5, 형식 검사 5/5 통과. 첫 알람은 산불 0.38, 굴뚝 0.33 으로 차이가 작았다. 아파트 단지 옆 연기라 배경이 공업 지역과 비슷하게 보일 수 있다.

굴뚝으로 판단하면 문장은 이렇게 바뀐다(모호, 반경 안 건물 4개).

```
굴뚝 아님: ... 위험도 높음: 반경 안에 주거지나 건물이 있다. 접근해 위치를 다시 확인할 것.
굴뚝:      ... 위험도 낮음: 건물 설비의 연기로 보인다. 확인을 권한다. 접근해 위치를 다시 확인할 것.
```

### 주의할 점

- 굴뚝 판단은 배경(공장 지대)에 기댄다. 주택가 굴뚝이나 비닐하우스 난방 연기는 잘 못 찾는다
- 위험도를 낮추는 쪽이라 잘못 짚으면 실제 화재를 낮음으로 낼 수 있다. 산불 130장에서 0장이었지만 도시 근처 산불 사진은 적다.
  그래서 반경 안에 건물이 없으면 낮추지 않고 확인 필요로 둔다(2번 줄)
- CPU 하한 구성(gguf)에서는 묻지 않는다. 사진 전체 질문은 CPU 에서 40초가 넘는다

## 알람 지연 개선(7.4)과 합치기 (11/28)

7.4(`docs/latency.md`)에서 같은 사건이면 VLM 관찰을 한 번만 받고 갱신된 판에 다시 쓰도록 바뀌었다.
불꽃과 굴뚝도 연기 색처럼 사건 안에서 바뀌지 않는 관찰이라 같은 방식으로 맞췄다.

- 사건의 첫 관찰을 받을 때만 불꽃(조각)과 굴뚝(사진 전체)을 묻는다. 순서는 전과 같이 불꽃 → 굴뚝 → 구조화 관찰
- 불꽃 답은 관찰(`flame_visible`)에 들어가 함께 다시 쓰이고, 굴뚝 값은 `Publisher.chimney` 에 남아 갱신된 판의 위험도와 문장에 그대로 쓰인다
- 그래서 갱신된 판에는 VLM 질문이 늘지 않는다. 위 CPU 측정의 "마지막 갱신 16.2초"는 이제 생기지 않는다
