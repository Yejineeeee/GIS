# 설명 속도 줄이기 (WBS 7.2)

경량 VLM이 한 장을 설명하는 데 180.7초가 걸렸다. 목표는 10초다. 무엇이 시간을
잡아먹는지 찾아 19.6배 줄였다.

담당: 이예진 / 상태: 9.2초까지 줄임. 평가셋 100장(6.1)이 나오면 다시 재야 함

## 요약

| 단계 | 1장 처리 | 무엇을 바꿨나 |
|---|---|---|
| 시작 | 180.7초 | bitsandbytes 4bit nf4, CPU |
| 실행 방식 교체 | 35.1초 | llama.cpp GGUF Q4_K_M |
| 탐지 영역만 넣기 | 10.1초 | 프레임 전체 대신 연기 영역을 잘라 넣음 |
| 질문 줄이기 | 9.2초 | 지형과 퍼짐을 질문에서 뺌 |

모델은 네 단계 모두 Qwen2.5-VL-3B-Instruct이고 4bit다. **모델을 바꾸지 않고 줄였다.**

## 1. 느린 것은 모델이 아니라 실행 방식이었다

`tools/measure_vlm.py`가 잰 180.7초는 bitsandbytes의 4bit nf4를 CPU에서 돌린
값이다. bitsandbytes는 CUDA를 보고 만든 것이라 CPU에서 느리다. 현장 기기 기준이
GPU 없음이므로(`docs/device_spec.md`) CPU용으로 만든 llama.cpp의 GGUF 4bit로
다시 쟀다.

비교가 깨지지 않도록 아래를 같게 맞췄다.

| 항목 | 값 |
|---|---|
| 이미지 | `results/vlm_measure.csv`의 6장, thumbnail(1024, 1024) 적용 |
| 질문 | `measure_vlm.py`의 PROMPT 그대로 |
| 스키마 | 같은 5개 항목. lm-format-enforcer 대신 llama-server의 json_schema |
| 생성 | 최대 120토큰, 탐욕 디코딩, 반복 벌점 1.15 |
| 스레드 | 4 (기준 환경의 4코어) |

결과다. 6장을 3회 돌려 워밍업 1회를 뺀 12건의 중앙값이다.

| | bitsandbytes nf4 | GGUF Q4_K_M |
|---|---|---|
| 1장 처리 | 180.7초 | 35.1초 |
| 첫 토큰 | 51.4초 | 31.8초 |
| 입력 토큰 | 829 ~ 872 | 886 |
| 최대 메모리 | 7.09GB | 5.17GB |
| 스키마 준수 | 18/18 | 12/12 |
| 일관성 | 18/18 | 10/12 |

6장 중 5장이 기존과 **글자까지 같은 답**을 냈다. 다른 한 장은 연기가 있다고
해놓고 색과 퍼짐을 없음으로 답했고, 그것이 일관성 10/12의 원인이다.

기기가 다르다는 점은 감안해야 한다. 180.7초는 박서연 노트북 WSL2(CPU 4코어,
메모리 8GB, 스왑 0)에서 쟀고, 35.1초는 이예진 노트북 윈도우에서 스레드 4개로
쟀다. 메모리 상한 8GB는 걸지 않았다. Q4_K_M이 5.17GB를 쓰므로 8GB가 발목을
잡지는 않는다.

## 2. 병목이 생성에서 입력 처리로 옮겨갔다

35.1초를 쪼개면 생성이 3.5초고 나머지 31.8초가 입력 886토큰을 처리하는 시간이다.
그 886토큰의 대부분은 이미지 토큰이다. **모델을 더 줄이는 것으로는 얻을 것이
없고, 이미지 토큰 수를 줄여야 한다.**

## 3. 토큰 상한을 낮추면 연기를 놓친다

llama-server의 `--image-max-tokens`로 상한을 낮춰 가며 쟀다. 탐지가 되는 5장
기준이다(워밍업과 같은 사진 1장은 캐시에 걸려 제외).

| 상한 | 입력 토큰 | 1장 처리 | 기존과 같은 답 |
|---|---|---|---|
| 1024 | 886 | 36.72초 | 4/5 |
| 512 | 589 | 23.57초 | 4/5 |
| 256 | 361 | 14.59초 | 5/5 |
| 128 | 229 | 9.81초 | **3/5** |

시간은 토큰에 거의 비례한다. 토큰당 0.027초에서 0.037초다.

상한 128에서 9.81초로 목표 안에 들어왔으나 **연기 사진 5장 중 2장을 "연기 없음"
으로 답했다.** 사진 전체를 뭉개는 방식이라 작은 연기부터 사라진다. 놓치는 것이
헛걸음보다 나쁘다는 것이 이 과제의 원칙이므로(`docs/buildings.md`) 이 길은
쓰지 않는다.

512가 하나 놓치고 256이 안 놓친 것은 상한마다 5장을 한 번씩만 돌린 결과라
둘을 줄 세울 근거가 못 된다. 확실한 것은 128에서 놓침이 두 배로 늘었다는 것뿐이다.

## 4. 탐지 영역만 잘라 넣으면 놓치지 않는다

YOLO가 낸 연기 영역을 원본에서 잘라 넣는다. 탐지도 자르기도 원본(3840x2160)에서
한다. 1024x576으로 줄인 것에서 탐지하면 작은 연기가 사라진다. 960px를 고른 이유가
그것이다(`docs/train_results.md`).

탐지가 된 4장 기준이다. 구름과 굴뚝연기 2장은 탐지가 0개라 자르지 않았다. 실제
파이프라인이라면 알람 자체가 뜨지 않는 경우다.

| 조건 | 입력 토큰 | 1장 처리 |
|---|---|---|
| 전체 프레임 | 886 | 35.34초 |
| 여백 1배 | 188 | 10.07초 |
| 여백 2배 | 424 | 20.11초 |
| 여백 3배 | 818 | 44.55초 |

여백 3배는 토큰이 전체 프레임과 비슷해 이득이 없다. 시간이 전체 프레임보다 길게
나온 것은 다른 날 쟀기 때문이므로 그대로 비교하면 안 된다.

**상한 128(229토큰)과 여백 1배(188토큰)는 토큰 수가 비슷한데 결과가 갈린다.**
뭉개서 줄이느냐 잘라서 줄이느냐의 차이다.

## 5. 항목마다 결과가 다르다

기존 측정과 답이 같은 비율이다. 4장을 3회씩 돌렸다.

| 조건 | 연기 유무 | 연기 색 | 퍼짐 | 불꽃 | 지형 |
|---|---|---|---|---|---|
| 전체 프레임 | 12/12 | 9/12 | 9/12 | 12/12 | 12/12 |
| 여백 1배 | 12/12 | 12/12 | 6/12 | 12/12 | 9/12 |
| 여백 2배 | 10/10 | 10/10 | 5/10 | 10/10 | 5/10 |
| 여백 3배 | 12/12 | 12/12 | 9/12 | 12/12 | 9/12 |

여백 2배가 10건인 것은 측정 중 기기가 절전으로 들어가 2건을 버렸기 때문이다.

- **연기를 놓치는 일이 없다.** 어느 여백에서도 12/12다
- **연기 색은 오히려 좋아진다.** 9/12에서 12/12로 올랐다. 연기가 화면을 채우니
  색을 더 잘 본다
- **퍼짐과 지형이 틀어진다.** 연기만 잘라내면 얼마나 퍼졌는지 견줄 대상이 없고,
  주변을 버렸으니 지형을 볼 근거가 없다

## 6. 망가지는 두 항목은 VLM이 답할 필요가 없다

- **지형**은 `land_use`의 용도지역 비율이 답한다. 사진을 보고 "산림 같다"고
  말하는 것보다 폴리곤이 정확하다
- **퍼짐**은 탐지 마스크의 화면 면적비로 낸다. 스키마에 `evidence.area_ratio`
  자리가 이미 있다

그래서 VLM에는 연기 유무와 색과 불꽃만 묻는다. 세 항목으로 줄여 다시 쟀다.

| 조건 | 입력 토큰 | 출력 토큰 | 1장 처리 | 세 항목 일치 |
|---|---|---|---|---|
| 5항목 + 잘라넣기 | 188 | 51 | 10.07초 | 12/12 |
| 3항목 + 잘라넣기 | 163 | 35 | **9.17초** | 12/12 |

출력 토큰이 30% 줄었고 질문이 짧아져 입력도 줄었다. 남은 세 항목의 정확도는
그대로다.

## 한계

- 숫자가 전부 **사진 4장에서 6장** 규모다. 6.1 평가셋 100장이 나오면 한 번에
  다시 재야 한다
- 측정 시점이 섞여 있다. 같은 표 안에서도 다른 날 잰 값이 있고, 기기 상태에
  따라 30%까지 차이가 났다. 연달아 잰 값끼리만 비교해야 한다
- 기준 환경(CPU 4코어, 메모리 8GB, 스왑 0)이 아니라 이예진 노트북 윈도우에서
  스레드만 4개로 묶어 쟀다. 메모리 상한은 걸지 않았다
- 잘라 넣기는 **탐지가 먼저 성공해야** 성립한다. 탐지가 놓치면 VLM까지 가지 않는다
- GGUF는 변환하지 않고 미리 양자화된 것(`ggml-org/Qwen2.5-VL-3B-Instruct-GGUF`)을
  받아 썼다. 변환 절차를 저장소에 남기는 것이 남아 있다

## 측정할 때 걸린 것

같은 사진을 여러 번 보내면 llama-server가 이미지 임베딩을 캐시해 입력 토큰이
1개로 떨어진다. 그 값은 캐시 적중 시간이지 처리 시간이 아니다. 처음 측정에서
4.8초가 나왔는데 전부 버렸다. `--slot-save-path`를 주고 띄운 뒤 요청마다 슬롯
캐시를 비워야 한다.

```
POST /slots/0?action=erase
```

기존 측정(`measure_vlm.py`)에는 이런 캐시가 없으므로, 비우지 않고 잰 값을 그대로
비교하면 거짓 수치가 된다.

## 다시 돌리는 방법

llama.cpp 윈도우 CPU 빌드와 GGUF 두 개를 받는다.

```
ggml-org/Qwen2.5-VL-3B-Instruct-GGUF
  Qwen2.5-VL-3B-Instruct-Q4_K_M.gguf        1.93GB
  mmproj-Qwen2.5-VL-3B-Instruct-f16.gguf    1.34GB
```

```
llama-server -m Q4_K_M.gguf --mmproj mmproj.gguf -t 4 -tb 4 -c 8192 -np 1 \
    --slot-save-path 슬롯폴더 --host 127.0.0.1 --port 8099

python tools/prep_images.py . 이미지폴더
python tools/prep_crops.py . runs/smoke_1260_960/weights/best.pt 자른폴더 1 2 3
python tools/measure_gguf.py --images 이미지폴더 --out results/gguf_measure.csv
python tools/sweep_tokens.py --server llama-server.exe --model Q4_K_M.gguf \
    --mmproj mmproj.gguf --images 이미지폴더 --out results/sweep_tokens.csv
python tools/measure_short.py --images 자른폴더/m1 --out results/short_m1.csv
```
