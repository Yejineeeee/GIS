# 검증기 조각을 줄였을 때 (WBS 4.7, 7.2 보충)

후보 검증기는 탐지 조각을 448px 로 키워 "이 사진에 연기가 있는가"를 묻는다. CPU 스레드 4개에서 한 번에
11.9초가 걸려 목표 10초를 넘는다(`docs/model_size.md`). 조각을 360, 300, 224px 로 줄였을 때 정확도와
시간을 쟀다.

담당: 이예진 / 상태: 측정 완료(11/18). 가속기가 있으면 448 을 그대로 두고, CPU 만 있으면 360 을 권한다

## 방법

`tools/vlm_verify_px.py`. 자르는 범위(탐지 박스 사방 25%)와 질문, P(예) 계산은 검증기와 같고 모델에 넣는
크기만 바꿨다. 정확도는 GPU(bitsandbytes 4bit nf4, 지금 검증기)로 쟀고, 448 은 저장돼 있던 검증기 값과
두 세트 모두 같게 나왔다(최대 차이 0.0000).

- Qwen2.5-VL 의 이미지 처리기는 256x256 보다 작은 그림을 키운다(파이프라인의 min_pixels). 224 를 제대로
  재려고 이 도구에서는 이 하한을 낮췄다. 224 를 쓰려면 파이프라인의 같은 값도 고쳐야 한다
- CPU 시간은 `tools/vlm_gguf_compare.py verify --px` 로 llama-server(GGUF Q4_K_M, 스레드 4)에 같은 조각 20개를
  크기마다 넣어 쟀다. 전원 연결

```
python tools/vlm_verify_px.py --dets runs/verify_real/verify_real.jsonl \
    --images data/eval_100/images/eval --out results/verify_px_eval.jsonl
python tools/vlm_gguf_compare.py verify --px 360 --dets runs/verify_real/verify_real.jsonl \
    --images data/eval_100/images/eval --out runs/compat/cpu_px360.jsonl --limit 20
```

## 결과

### 평가셋 확정본 (탐지 177개: 연기 131, 헛탐지 46)

| 조각 | 입력 토큰 | AUC | 연기 남김 (0.7) | 헛탐지 거름 (0.7) | 새로 놓친 연기 사진 | 연기 95% 남기는 문턱 | 그때 헛탐지 거름 |
|---|---|---|---|---|---|---|---|
| **448 (지금)** | 295 | **0.916** | 127/131 | **41/46** | 1장 | 0.80 | **41/46** |
| 360 | 183 | 0.903 | 121/131 | 38/46 | 3장 | 0.53 | 36/46 |
| 300 | 139 | 0.901 | 117/131 | 40/46 | 4장 | 0.38 | 29/46 |
| 224 | 103 | 0.899 | 118/131 | 38/46 | 3장 | 0.50 | 24/46 |

### 장소를 섞은 150장 (탐지 165개: 연기 135, 헛탐지 30)

| 조각 | AUC | 연기 남김 (0.7) | 헛탐지 거름 (0.7) | 새로 놓친 연기 사진 | 그때 헛탐지 거름 (연기 95%) |
|---|---|---|---|---|---|
| 448 (지금) | 0.738 | 121/135 | 14/30 | 2장 | 11/30 |
| **360** | **0.770** | 121/135 | 15/30 | 3장 | **14/30** |
| 300 | 0.731 | 115/135 | 14/30 | 4장 | 4/30 |
| 224 | 0.671 | 111/135 | 12/30 | 4장 | 5/30 |

### CPU 시간 (스레드 4, 같은 조각 20개)

| 조각 | 입력 토큰 | 1회 중앙값 | 448 대비 | 10초 넘은 것 |
|---|---|---|---|---|
| 448 | 295 | 17.3초 | 1 | 20/20 |
| **360** | 208 | **10.0초** | **0.58** | 8/20 |
| 300 | 160 | 8.5초 | 0.49 | 0/20 |
| 224 | 103 | 4.9초 | 0.28 | 0/20 |

이번 448 값(17.3초)은 11/18 새벽에 같은 조건으로 잰 11.9초보다 길다. 같은 실행 안에서 크기만 바꿔 쟀으므로
비율은 쓸 수 있다. 11.9초에 비율을 곱하면 360 은 7초쯤, 300 은 6초쯤, 224 는 3.4초쯤이다(어림값).

## 읽히는 것

- **360 까지는 가르는 힘(AUC)이 거의 그대로다.** 평가셋 0.916 → 0.903, 150장은 오히려 0.738 → 0.770 이다
- **그러나 문턱을 그대로 두면 연기를 더 놓친다.** 0.7 에서 연기 탐지 남김이 127 → 121, 새로 놓친 연기 사진이
  1 → 3장이다. 조각이 작아지면 확률이 전체적으로 내려가서다. 360 을 쓰면 문턱을 다시 정해야 한다
- **300 과 224 는 순서는 비슷해도 실제로 거르는 힘이 무너진다.** 연기를 95% 남기도록 문턱을 내리면 평가셋에서
  헛탐지를 29/46, 24/46 만 거른다(448 은 41/46). 150장에서는 4/30, 5/30 이다
- **시간은 토큰 수에 비례한다.** 360 은 448 의 0.58배, 224 는 0.28배다

## 정리

| 기기 | 검증기 조각 | 이유 |
|---|---|---|
| 가속기가 있는 기기 (내장 GPU, NPU, 소형 GPU) | 448 그대로 | 1회 1~6초라 줄일 이유가 없다(`docs/compat.md`) |
| CPU 만 있는 기기 | **360**, 문턱을 다시 정함 | 정확도를 거의 잃지 않고 시간이 0.58배다. 10초 안팎에 든다 |

300 과 224 는 권하지 않는다. 빨라지지만 헛탐지를 거르는 힘이 크게 준다.

## 한계

- 360 의 문턱을 새로 정하지 않았다. 같은 177개로 정하면 평가셋에 맞춰지는 셈이라, 다른 사진으로 정해야 한다
- CPU 시간은 20개로 잰 값이고, 448 의 절대값이 이전 측정과 달랐다
- 정확도는 GPU 실행 방식(bitsandbytes)으로 쟀다. CPU 실행 방식(GGUF)에서도 같은 경향인지는 20개의 답만 봤다
- 평가셋은 장소 두 곳이고, 150장 중 117장은 탐지 모델이 학습한 영상이다
